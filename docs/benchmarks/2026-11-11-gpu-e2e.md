# Is a GPU worth it? End-to-end, CPU vs GPU on one T4 (2026-11-11)

**Verdict: not for the default path, and not yet for any engine.** A GPU makes
docling 6–8× faster and GLM-OCR 3.4× faster again with vLLM, but on these scans
neither engine becomes more faithful, and both stay less faithful than the
default path that a GPU barely speeds up (15.1 → 10.4 s a scanned page, with 3
of 42 pages coming out differently from CPU). The cheaper win is on the CPU:
overlapping the default path's independent stages (ADR-056, section 4) takes a
scanned page from 11.4 to 8.5 s on 4 cores, byte-identical. Reopen the GPU
question only if docling (or another engine) is shown to beat the default path
on documents where fidelity matters, which this sample (38 scans, 4 born-digital
pages) cannot show.

## Method

- Every timing is the backend's real conversion (`file_to_markdown`), not one
  model: engine selection, OCR, the table and layout passes, structure recovery,
  the serializer and the normalizer. docling-serve and the GLM-OCR service run
  locally and are reached over HTTP, as in production.
- One Kaggle machine per run (Tesla T4, 4 vCPU Xeon @ 2.0 GHz, 31 GB), CPU leg
  then GPU leg, so the columns differ only in the device. CPU legs hide the GPU
  (`CUDA_VISIBLE_DEVICES=`).
- Pages: sets A–D (`regions.py`), the 42 pages with references that docling and
  GLM-OCR were already scored on (38 scanned, 4 born-digital), each a one-page
  PDF; plus whole documents: Vol 4 No 1 (36 scanned pages) and Vol 5 No 1 (30).
  One untimed warm-up conversion per leg (model loads) is reported separately.
- The backend's own metrics say which engine produced each page; a remote
  engine's fallback counts as a failure. **No page fell back in any leg.**
- Accuracy: `score.py`'s `score_page` against the references (wer, cer, word
  recall, digit recall).
- Harness: `benchmarks/bakeoff/kaggle/{e2e.py,e2e_kernel.py,gpu_device.py,
  push_e2e.sh,e2e_report.py}`. Raw outputs: `benchmarks/bakeoff/outputs/
  kaggle-e2e-20261111{,-v3,-v4}/` (kernel `thomasamann/wiseau-gpu-e2e-run`,
  private; v2 image + GLM-OCR, v3 a replicate of both, v4 docling + vLLM).
- Versions: Kaggle torch 2.11.0+cu130 (backend and GLM-OCR), transformers
  5.22.1, tesseract 5.3.4, glmocr 0.1.5; docling-serve 1.38.2 (torch 2.15.0,
  EasyOCR 1.7.2) in its own virtualenv; vLLM 0.33.0 in its own.
- The default path's two model passes are moved to the GPU by the harness
  (`gpu_device.py`: weights fp32, outputs back to CPU before post-processing);
  production has no device setting.

Scanned pages, mean seconds (median, max); born-digital mean; whole documents.

| docling, GPU | **6.5** (6.0, 12.0) | 5.5 | **218 s** | – | 0.275 | 0.878 |

† The three pages V2 p9, V4 p27, V5N1 p18 only; fp16 on those pages scores the
same as fp32 (0.005 / 0.084 / 0.092 wer). ‡ Born-digital pages never go to
GLM-OCR (ADR-036): the local parser reads their text layer.

- **Replicate.** v3 re-ran the default-path and GLM-OCR legs on another
  machine: 14.8 / 12.4 / 10.3 s (CPU 1, CPU 4, GPU) and 40.5 s (GLM-OCR fp16),
  all within 2% of the table; the same three pages differed CPU vs GPU.
- **GPU memory:** default path ~1.1 GB (torch peak); docling-serve up to 10.0 GB
  (nvidia-smi, mean utilisation 15%); vLLM 10.6 GB (it reserves 60% of the card by
  configuration), transformers GLM-OCR up to 9.3 GB.
- **Cold start (warm-up page):** default path 46 s CPU / 25 s GPU; docling 44 s
  CPU / 12 s GPU after a ~24 s service boot; vLLM 141 s to boot, then 16 s.

### Default path: CPU vs GPU output

- CPU 1 thread vs CPU 4 threads: **44/44 files byte-identical** (42 pages, two
  whole documents), in both runs.
- CPU vs GPU: 39/42 pages identical, and Vol 4 No 1 differs. On V4 p14, p17 and
  p22 every word is the same, but a heading or one paragraph moves to another
  place: the layout detector's boxes differ in the last bits on the GPU, and a
  line near the 50% region-overlap rule tips the other way. The GPU is stable
  run to run (42/42 identical across two GPU runs).

## Reading it

1. **Default path.** The GPU saves 4.7 s of 15.1 on a scanned page (and nothing
   on born-digital pages, DOCX or URLs). Tesseract, which has no GPU path, is
   most of what is left. A paid GPU for a third off scanned pages, with output
   that differs from CPU on 7% of them, is not worth it. Four CPU threads give
   half the gain with identical output, and overlapping the stages more (§4).
2. **docling.** The GPU turns docling from 42 s to 6.5 s a scanned page and from
   29 minutes to under 4 for a 36-page journal, with the same accuracy. But that
   accuracy is wer 0.27 against the default path's 0.06 on the same pages: on
   these scans docling is the less faithful engine at any speed, and on
   born-digital pages it costs 5.5 s against 0.3. A GPU makes docling practical,
   not better.
3. **GLM-OCR.** vLLM matters: 41.9 → 12.4 s a page on the same GPU; on the three
   pages the CPU leg also ran, 7.1 s against 200 s (28×). Accuracy is unchanged (wer 0.085 over 42 pages), still below the
   default path's 0.063, and it is no faster than the default path on four CPU
   cores with overlap (8.5 s).
4. **CPU-side speed (ADR-056).** See the section below.

## 4. Overlapping the default path's stages on the CPU (ADR-056)

A scanned page's time, 4 CPUs, six pages: guard OCR 4.5 s (37%), layout 2.9 s
(24%), psm 3 2.8 s (23%), tables 1.8 s (15%), the rest 0.1 s. These ran one after
another, but psm 3 is its own Tesseract process and both models need only the
page image. ADR-056 runs them beside the guard. The page images are still
rendered on the calling thread, and the results are combined in the same order.

Measured in this repo's container (4 vCPU), `main` (`21ba98d`) against the
branch, same pages and documents:

| | `main` | sequential (`WISEAU_OCR_OVERLAP=0`) | overlap |
|---|---|---|---|
| 4 CPUs, 42 pages, scanned s/page | 11.7 | 11.8 | **8.3** |
| 4 CPUs, Vol 4 No 1 (36 pp) | 430 s | – | **308 s** |
| 2 CPUs, 6 pages | – | 12.0 | **8.8** |
| 1 CPU, 6 pages | – | 11.6 | 12.3 |
| 4 conversions at once, 8 pages, cold start | 58.6 s | – | 58.0 s |

- **Byte-identical to `main`:**
  - 42/42 pages and the 36-page document;
  - every 1- and 2-CPU leg, overlap on and off;
  - the eight pages converted four at a time from a cold start.
- **On 1 CPU overlap only adds overhead,** so the default (`auto`) overlaps on
  2+ CPUs.
- **With 4 conversions at once the cores are already busy:** a single
  conversion gets faster, not throughput.
- **A first run on 2 CPUs found a model-loading race,** fixed before these
  numbers (ADR-056): the layout model lost every page's layout pass.

## What would reopen it

- Documents where an ML engine is clearly *more faithful* than the default path:
  complex born-digital layouts (multi-column with tables, forms) are the likely
  case, and this sample holds only four born-digital pages. A gold set of those,
  scored on CPU, is the next experiment; the GPU only matters once an engine has
  earned its place on fidelity.
- A host with a GPU already available, where the cost question disappears.

## Run notes (what went wrong on the way)

- v1 started before its dataset finished processing (no inputs); `push_e2e.sh`
  now waits for it.
- v2: Kaggle's Python has no working `ensurepip`, so `python -m venv` failed and
  the docling and vLLM legs never started; the kernel now uses `virtualenv`.
- v3 attached the previous dataset version and re-ran every leg (hence the
  replicate). docling-serve 1.27.0 (the Space's tag) failed at import against
  today's unpinned `docling-jobkit`; vLLM 0.22.1's transformers does not know
  `glm_ocr`. v4 used docling-serve 1.38.2 and vLLM 0.33.0, and the kernel itself
  carries the leg selection.
