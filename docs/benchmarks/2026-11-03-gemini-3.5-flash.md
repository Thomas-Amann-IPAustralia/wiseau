# Gemini 3.5 Flash on the bake-off sample — 2026-11-03

This run adds Gemini 3.5 Flash (`gemini-3.5-flash`, a cloud API) to the three
self-hosted engines from the [2026-11-02 re-run](2026-11-02-bakeoff-rerun.md). It
used the same 10 pages, the same committed references and the same scorer
(`benchmarks/bakeoff/`), so all four rows compare directly.

## Budget and how it was enforced

The user set a **hard limit of $1.00**. `benchmarks/bakeoff/run_gemini.py` enforces it
on the client side, because nothing here can set a cap on the Google billing account:

- **Prices:** Google's pricing page did not list `gemini-3.5-flash` on 2026-11-03. The
  script uses the rates third-party trackers consistently report: **$1.50 per 1M input
  tokens and $9.00 per 1M output tokens**, with thinking billed as output.
- **Ledger:** `outputs/gemini-3.5-flash/spend.json` persists across runs, so the smoke
  test counted against the budget.
- **Pre-flight check:** before each request, the input is counted with the free
  `countTokens` call, and the request is priced at its worst case, the full output
  allowance. If ledger + worst case would exceed $1.00, the request is not sent.
- **Failures:** no retries. A failed request is booked at its worst case, because it
  may still have been billed.

**Ledger total: $0.72**, out of 12 requests:

| Requests | Booked as |
|---|---|
| 1 smoke test + 9 sample pages | $0.49, from Google's billed token counts |
| 2 failed requests (HTTP 502) | $0.23 combined, at worst case ($0.08 + $0.15); possibly not billed at all |

**Smoke test:** V4 p26 was sent first. The transcription was correct, the response
finished normally, and it cost $0.034 (1,163 input and 3,603 output tokens, 2,951 of
them thinking). That page's output is reused as its sample result, since the settings
were identical.

## Setup

- **Input:** each page as a 200-dpi PNG, the resolution GLM-OCR renders at, so every
  ML engine reads the same pixels. The PDF text layer is not sent.
- **Prompt:** transcribe exactly as printed, in reading order, tables as Markdown
  tables, skip text inside photographs (see `PROMPT` in the script).
- **Settings:** `temperature` 0; `maxOutputTokens` 8,192, which includes thinking.

## Findings

1. **Scans: Gemini 3.5 Flash is the most faithful engine tested, by a wide margin.**
   - Reading-order error is 0.034, against 0.103 for GLM-OCR. It finds 99.6% of words
     and 99.3% of numbers, and almost nothing it writes is off the page.
   - On the typewriter table that defeats both self-hosted ML engines (V2 p17), it
     finds 98% of words and 99.5% of numbers.
   - It is about 5× faster than GLM-OCR on CPU (22 s per page).
2. **Its errors are few, but they are the dangerous kind:**
   - **Dropped a row:** on V2 p17 the FLOWER SIZE values row ("very large / very
     large / medium large / medium") is missing. The heading is written, but its cells
     are empty.
   - **Silently corrected the source:** the page prints "Alsmeer" in the prose, and
     Gemini wrote "Aalsmeer", the correct Dutch spelling. That is a nicer reading, but
     it is not a faithful one.
   - The 2026-11-01 run saw the same pattern from GPT-5.4 ("Wonthaggi" for *Monbulk*).
     A cloud VLM's mistakes look plausible, so they are harder to catch than OCR
     garbage.
3. **V16 p90 was cut off by the output limit, not misread.** The page has about 100
   names with up to three numbers each. Thinking plus table markup used up the
   8,192-token allowance about a third of the way down (`finish=MAX_TOKENS`). What it
   did write is correctly paired, with nothing off the page (word precision 0.997,
   number precision 1.000). It is the only ML engine that paired those side-by-side
   tables correctly as far as it got.
   - A retry at 16,384 tokens failed with HTTP 502. A long generation probably
     outlasts the gateway, and the 8,192 version already took 30 s. It was not retried
     again, to protect the budget.
   - Dense pages need a lower thinking level or streaming output, or to be split.
4. **Born-digital pages:** without p90, Gemini is near-exact (wer 0.040, every number
   found). PyMuPDF reading the text layer is still exact, free and instant, so there is
   no reason to send born-digital pages to a cloud model.

## Cost per page

Excluding the failed requests, the average was **$0.050 per page** (range $0.024–0.075).
Thinking tokens were most of it, about 80% of output on the smoke page. At that rate:

- **The three sample journals (168 pages):** about $8.
- **Scanned pages only (60 pages):** about $3.

## Caveats

- **Small sample:** 10 pages, one run each, at temperature 0. The model is still
  stochastic.
- **Unofficial prices:** the rates are third-party listings, not Google's page. The
  ledger's dollar figures are therefore estimates. The token counts are exact.
- **Different from 11-01:** this is a different model from the 11-01 "Gemini 3.8
  Flash", and it was scored on the new references, so it is not directly comparable
  with that row.
- **Project direction:** sending documents to a cloud API goes against the project's
  self-hosted stance (see the 11-01 post-mortem). This run measures what that costs in
  fidelity; it does not recommend adopting it.
