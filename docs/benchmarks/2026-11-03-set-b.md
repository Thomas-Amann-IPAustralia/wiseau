# Set B: ten new, independently transcribed scanned pages: 2026-11-03

**Why:** every earlier comparison of the self-hosted engines rested on six scanned
pages whose answer keys were drafted from Tesseract output and then corrected.
That could flatter Tesseract, and six pages is too few to base a design on. Set B
adds ten pages whose answer keys were written from the page images alone, before
any engine was run on them.

No paid API was used. Everything here ran on the session's container: 4 vCPU,
15 GB RAM, no GPU. Engines ran one at a time.

## How the pages were chosen

1. **Survey:** all 62 image-only pages in the three PDFs (V2: 28, V4: 32, V16: 2)
   were run through Tesseract once. That gave each page's word count, number share
   and whether the column detector (ADR-035) finds columns.
2. **Layout groups:** pages were assigned to five groups. "Two-column prose" (22
   pages) has two columns and under 12% numbers. "Tables" (8 pages) is at least 30%
   numbers. "Two-column + data" (13 pages) has two columns and 12–30% numbers.
   "Single column" has 11 pages. Near-empty pages (8, such as covers, blanks and
   photo pages) were left out.
3. **Seeded random draw:** 3 + 2 + 3 + 2 pages, seed 20261103, excluding set A's
   six scanned pages.
4. **Duplicates found and replaced.** V2's PDF scans four journal pages twice:
   p15 = p5, p16 = p6, p17 = p13 and p18 = p14. These were found by mapping each
   scan to its printed page number.
   - The draw first picked V2 p13 (journal page 11, the same page as set A's V2
     p17) and V2 p16 (journal page 4, the same page as set A's V2 p6).
   - They were redrawn from their groups with seeds 20261104 and 20261105, which
     gave V2 p14 and V2 p23.
   - This also means set A's V2 p17 is one of a duplicate pair.

| Two-column + data | V4 p8 (pumpkin table + prose), V4 p22 (rose table + prose), V4 p25 (application lists) |
| Single column | V2 p2 (contents), V4 p27 (dense directory, many phone numbers) |

## How the answer keys were made

1. **Blind transcription.** Each page was transcribed by reading high-resolution
   crops of the page image, before any engine was run on set B. These were
   committed as they stood (`88b99f4`), so any later change shows up as a diff.
2. **Conventions, as in set A:**
   - reading order is column by column;
   - tables are read row by row, with a cell's lines read across;
   - text inside photographs is skipped;
   - the page number comes last;
   - printed typos are kept as printed ("cserrations", "tne").
3. **Adjudication.** `benchmarks/bakeoff/disagreements.py` aligns each engine's
   output to the reference and lists the words where engines read something else.
   - Agreement counts per recogniser family: the two Tesseract runs count once,
     and docling's EasyOCR and GLM-OCR are the other two.
   - Each listed word was checked against a zoomed crop. The reference was changed
     only when the image showed it was wrong.
   - Every change is in `benchmarks/bakeoff/adjudication/log.md`.

## Adjudication outcome

There were two rounds. In the first, Tesseract and EasyOCR were compared with
the references. In the second, GLM-OCR was added. Eighteen words were flagged and
checked against zoomed crops, and **none was a transcription error**. They were
character confusions (A/4, B/8, D/0, a sans-serif capital I read as l), faint
letters, numbers and units printed with a space, and differences in the order
words were read. The only change to any blind transcription was V2 p23 "the" →
"tne". That was made on self-check, before any engine output was read. The details
are in `benchmarks/bakeoff/adjudication/log.md`.

## Findings

1. **"Is Tesseract better than GLM-OCR?" It depends on the layout, and the
   independent references confirm it.**
   - **Tesseract wins on tables and single-column pages.** On the V2 p14
     typewriter table it scores wer 0.106 and finds 88% of numbers. GLM-OCR scores
     0.407 and finds 71%. That reproduces set A's V2 p17 result on a page whose
     reference was *not* drafted from Tesseract, so the table result is not a
     reference artefact.
   - **GLM-OCR wins, often by a lot, on multi-column pages that mix prose with
     photos or data.** Examples: V2 p9 0.005 against 0.290, V4 p8 0.061 against
     0.241, V4 p22 number recall 0.991 against 0.820.
   - Overall GLM-OCR has the better word order (0.088 against 0.135), with about
     the same word and number recall, at about 25 times the time.
2. **The ADR-035 reading-order fix holds on unseen pages.** Without it, Tesseract's
   wer is 0.505; with it, 0.152. Word content is identical.
3. **Two Tesseract-path bugs found, not yet fixed:**
   - **Photos are OCR'd as text.** The default path reads garbage out of
     photographs. This is most of its loss on V2 p9 and V2 p11 (word precision
     0.854 in the prose group). Tesseract psm 3 recognises image regions and skips
     them, which is why it scores 0.030 on those pages.
   - **Rows get merged.** `reading_order._rows` merges lines by comparing against a
     row's *growing* extent. One OCR line box two printed lines tall (26 pt, where
     the median is 15) chained three printed lines into one row on V2 p11.
   - They were deliberately not fixed here, because a fix tuned on set B would
     stop set B being a fair test.
4. **docling is not competitive on scans.** It is the worst or near-worst engine in
   every group, and its number recall is 0.75–0.78.
5. **Voting is beaten by routing.** Voting reaches wer 0.063 at 132 s/page. Choosing
   one engine per page reaches 0.039 at 58 s/page.
6. **A simple router gets almost all of the per-page headroom.** "≥ 30% numbers or
   single column → Tesseract, else GLM-OCR" uses only signals the default path
   already computes in its first ~3 s.
   - It scores within 0.004 wer of the oracle on all 16 pages.
   - It picks the oracle's engine, or one within 0.01 wer of it, on 14 of 16 pages.
     The two misses (V4 p26, V2 p23) are pages where docling was best by about 0.03
     over GLM-OCR; the router never picks docling.
   - On set A it matches the paid Gemini run's word order. It still trails Gemini
     on numbers (0.954 against 0.993).

## Caveats

- 16 scanned pages from two journals of one publication, so it is a narrow corpus.
  The router's threshold was chosen after seeing set B; set A is a fairer check,
  but it is only six pages. A third, untouched set is needed before the threshold
  is trusted.
- **Reference conventions.** Tables are read line by line across each row. GLM-OCR
  and psm 3 read a multi-line cell as a unit, which costs them some wer on V2 p14's
  flower-colour row, but no bow/num.
- **Timings** are this container's (4 vCPU, no GPU). GLM-OCR's 87–106 s/page would
  be far lower on a GPU.
- **Faithful but not structured.** No metric here scores Markdown *structure*
  (table markup, headings). Tesseract emits plain lines. GLM-OCR emits Markdown or
  HTML tables.

## Recommendation: the design these results support

The evidence covers scanned pages. Born-digital pages are already settled:
PyMuPDF reads their text layer exactly, at wer 0.019 and 0.2 s/page (ADR-036).

1. **Keep Tesseract + ADR-035 as the fast default for scans, and fix its two bugs
   before anything else.**
   - It is the best engine on tables and single-column pages, at ~3 s/page, and
     deterministic.
   - The two bugs in finding 3 are cheap, local and deterministic: skip OCR
     inside image regions, and group rows by line centre rather than by growing
     extent.
   - They are most of the default path's loss on photo pages. psm 3's 0.030 on
     those pages shows what removing photo noise buys.
   - Validate both on a fresh set C, not set B.
2. **Make the opt-in fidelity engine a per-page router, not "GLM-OCR for every
   scanned page".** This changes ADR-036's rule from "image-only → GLM-OCR" to
   "image-only and not table/single-column → GLM-OCR":
   - Always run Tesseract first (~3 s).
   - If the page is ≥ 30% numbers, or has a single column, keep Tesseract's text.
   - Otherwise send the page to GLM-OCR, with ADR-014's per-page fallback to
     Tesseract.
   - On all 16 pages this gives wer 0.039 instead of 0.088 (GLM-OCR alone), and
     number recall 0.948 instead of 0.907, in 58 s/page instead of 94. It is both
     more faithful *and* faster than today's opt-in.
   - Being a heuristic, it follows ADR-030: record which rule fired per page in the
     metrics/logs, and fall back to Tesseract rather than guess.
3. **Drop docling and voting for scans.**
   - docling is the weakest scan engine in every group. Keep it only where it
     earns its place (born-digital layout/structure, which this benchmark does
     not measure).
   - Voting costs all three engines and loses to routing.
4. **Do not train a model or call a paid API for this, yet.**
   - The offline router is within 0.004 wer of the per-page optimum on these pages
     and matches Gemini's word order on set A.
   - The remaining gap to Gemini is **numbers in tables and data pages** (router
     0.948 against Gemini 0.993 on set A). That is the one place a later
     investment (a table-specific model, or a fine-tune) would pay off. The
     benchmark should measure that gap first, on more table pages.
5. **Before shipping the router:** build set C (about 10 untouched scanned pages,
   blind-transcribed the same way, from new journals if possible). Re-check the
   30% threshold and the bug fixes on it. Set B has now been looked at too closely
   to serve as a test.
