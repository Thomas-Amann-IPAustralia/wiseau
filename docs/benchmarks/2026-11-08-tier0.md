## 0.1 The normalizer keeps printed punctuation (ADR-039)

`clean_markdown()` no longer rewrites ‘ ’ “ ” – — … to `' " - -- ...`. The
no-break space, zero-width space and BOM rows stay. API 0.13.0 → 0.14.0.

**Determinism check.** The default path was re-run on all 42 pages of sets A to D.
41 outputs differ from the frozen ones *only* by the old mapping: folding the new
output through it gives the frozen file byte for byte. One page is identical (it
has no such punctuation). So the re-run reproduced every OCR decision exactly,
and the cleaner change is the only difference.

**Born-digital volumes** (default path, OCR off), characters that used to be
flattened and are now kept:

hyphen row was not quietly creating Markdown lists.

## 0.3 Harness metrics

`score.py` adds `cer`, `ord`, `pun_r` / `pun_p` / `pun_rf`, and the run columns
`rss` and `fail` (definitions in [`benchmarks/bakeoff/README.md`](../../benchmarks/bakeoff/README.md)).
`edit_distance` is now Myers' bit-parallel algorithm. It matches the textbook
dynamic programme on 3,000 random pairs (lengths up to 70, past the 64-bit word
boundary), and every earlier metric in `results.json` is unchanged across 16
engines and 530 page scores. Scoring everything takes about 9 s.

`ord` is a line-level stand-in for block order: references record printed lines,
not blocks. It separates order from recognition as intended. On all 38 scans the
pre-ADR-035 path (`tesseract-unordered`, 20 pages) has `ord` 0.534; the
ADR-035/037 paths 0.213 and 0.194; today's default 0.113; GLM-OCR 0.120.

**Default path, all scored pages** (`pymupdf` after the re-run):

| Pages | wer | cer | ord | pun_r | pun_p | s/page | rss (MB) | fail |
|---|---|---|---|---|---|---|---|---|
| digital (4) | 0.019 | 0.011 | 0.047 | 1.000 | 1.000 | 0 | 424 | 0.00 |
| scanned (38) | 0.056 | 0.024 | 0.113 | 0.793 | 0.795 | 8 | 424 | 0.00 |

`rss` is the run's high-water mark (the runner process or the `tesseract` CLI),
not a per-page figure.

### What the punctuation score shows

| Pages | pun_r before → after | pun_rf (folded) before → after |
|---|---|---|
| digital (4) | 0.948 → **1.000** | 1.000 → 1.000 |
| scanned (38) | 0.879 → 0.793 | 0.964 → 0.963 |

Born-digital punctuation is now exact. The scanned drop is **not a fidelity
loss**: the folded recall, which ignores the printed form, did not move. It comes
from two things, both checked against page images at 600 dpi:

1. **The scanned references typed most curly quotes as straight.** They hold
   1,008 `'` and 189 ‘ ’. Tesseract emits ‘ ’ (523 / 591). On Vol 5 No 1 p11 the
   print clearly reads ‘Modern (a curly opening quote) where the reference has
   `'Modern`. The old cleaner flattened Tesseract's quotes to `'`, which happened
   to agree with the references. On the bold sans-serif headings of Vol 4 No 2
   (`'Saint Pierre'`) the glyph is ambiguous at this resolution.
2. **Tesseract reads printed en dashes as hyphens.** References hold 191 –, the
   output none. Vol 5 No 1 p11 prints true en dashes in `663–674` and in the
   table ranges (`11.0–23.5`). This is a recognition loss, and it was there before
   ADR-039 too: the old cleaner flattened – to `-` anyway.

So `pun_*` on the existing scanned references measures the transcribers' typing
convention as much as the engines. Until those references are adjudicated for
punctuation, judge scans on `pun_rf` and judge printed form on born-digital pages.
**New references (sets E and F) are transcribed with printed punctuation**: ‘ ’
“ ” – — as printed, and `'` only where the print is straight.

## 0.4 docling's JSON

- `docling_client.convert_document_full()` asks docling-serve for `md` and `json`
  (`to_formats` repeated) and returns both. `json_content` is the response key in
  docling-serve 1.27.0 (checked in its Gradio client). `convert_document()`, the
  conversion path, still asks for Markdown only, so the API contract is unchanged.
  Four new tests.
- The harness's `docling` engine (docling as a library) writes `<page>.json`
  beside each `.md`.

**Heading levels in the pinned docling.** The Space pins
`docling-serve-cpu:v1.27.0`. Its tagged `uv.lock` resolves `docling-slim` 2.113.0
and `docling-core` 2.87.1. That docling already has a `HeadingHierarchyModel`
stage, which sets heading levels from PDF bookmarks, then numbering
(PART I → 1. → 1.1 → (a) → (i)), then font style. It is off by default
(`HeadingHierarchyOptions.enabled = False`), and the style signal needs
`generate_parsed_pages=True`. **docling-serve 1.27.0 does not expose it**: its
request options have no heading field. Later docling does
(`do_pdf_heading_hierarchy` and `pdf_heading_hierarchy_options` in 2.149.0). So
turning it on needs a pin bump, which is a docling-Space change to test on its
own. It is the same signal order roadmap item 3.1 proposes for the default path,
which makes it a useful reference implementation.
